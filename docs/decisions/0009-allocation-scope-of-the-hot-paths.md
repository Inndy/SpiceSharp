# 0009. Allocation scope of the hot paths

- Status: Accepted
- Date: 2026-10-29
- Decided by: the human

- **Context:** the draft says MUST NOT allocate per frame or per message on hot paths.
- **Decision:** the hot paths are allocation-free: display draw messages (pooled payloads, pooled decode buffers, pinned surfaces), presents (fixed stack storage), input sends (queued into two reusable buffers), mouse motion and cursor moves (coalesced into fields, one cached delegate posted), audio writes (ring buffer). Allocations remain only on infrequent control paths: cursor shape changes and mouse-mode/agent/disconnect notifications (a closure posted to the UI thread), agent messages (clipboard, capabilities, monitors config), channel link and surface create.
- **Reason:** those happen at most a few times per user action, not per frame or per draw message. Accepted by the human on 2026-10-29 after the profiling below.
- **Profiling (2026-10-29, after the human asked):** live ETW allocation sampling under load and Codex's deterministic tests (task 11) found three per-event allocations that contradicted this section; all are fixed. (1) Every idle-to-busy channel send started a new async writer Task: the writer is now one long-lived loop per channel parked on a reusable `IValueTaskSource`; 10,000 warmed sends allocate 0 B on the sending thread. (2) Every decoded draw allocated its `DecodedImage` wrapper: released wrappers go to a per-thread free list (`DecodedImage.Rent`). (3) Every image draw formatted a statistics key string: keys are precomputed. Second-pass replays of all four fixtures now allocate only the surface buffers (0 B per draw message, 0 B for 10,000 cache hits). Cursor shapes: the Windows 8.1 QXL driver never uses the server's cursor cache (every SET has unique 0 and no CACHE_ME flag), so each shape change was a full decode plus a new HCURSOR (about 50 KB/s while sweeping a window of 24 cursors). The session now keeps the last 48 decoded shapes matched by content (header without the unique id, hash, then byte compare), so a repeat returns the same `CursorShape` and the viewer's HCURSOR cache hits; the same sweep then allocated nothing measurable. Still allocating, as this section allows: first decodes of new cursor shapes, surface creation, and first-use ArrayPool growth. Details: docs/verification/2026-10-29-live.md and docs/reviews/codex-verify.md (task 11).
