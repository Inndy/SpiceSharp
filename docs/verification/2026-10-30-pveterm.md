# 2026-10-30: PveTerm live check (termproxy serial console)

Commit hashes in this record name work-branch commits kept under the tag `archive/pveterm-wip`; they were squashed
into one commit on `main`.

- Host: the PVE node, Proxmox VE 9.2 (`/version` 9.2.24). Its API certificate validates against the Windows system
  roots with hostname checking, so PveTerm ran without a pinned CA ([0033](../decisions/0033-pve-api-tls-pins-a-given-ca-else-uses-system-trust.md)).
- Guest: `ubuntu` (Ubuntu 26.04 desktop, kernel 7.0). A serial port of type socket was added by the human. The human
  started a getty and then a logged-in `bash` with `TERM=xterm-256color` on `ttyS0`. No guest or Proxmox setting
  was changed by the agent.
- Credentials: the test API token. A read-only probe (`tools/pve-vv.py --term-probe`) showed `VM.Console` on the
  test VMs and no `Sys.Console`, so the node shell was not tried. No container is in scope.
- Build: `PveTerm.exe` from the Native AOT publish (win-x64, 5,101,568 bytes), started by
  `tools/pve-vv.py --term qemu:<vmid>:serial0 --hidden` under the test harness's pseudoconsole
  (`Pve.Term.Tests.exe --conpty-run`). No window was shown.
- Client: Windows 11 build 26100.9711; the pseudoconsole host is the in-box conhost 10.0.26100.9549.

## What ran and what happened

| Check | Result |
|---|---|
| Hand-off | The helper served the descriptor once through the user-only pipe; `hand-off served`. |
| Session request | PveTerm itself POSTed `.../qemu/<vmid>/termproxy` with `serial=serial0` and the API token, then opened `vncwebsocket` and sent the `user:ticket` line. termproxy answered `OK`, then `starting serial terminal on interface serial0`. So token-authenticated serial termproxy works on this PVE version (the survey's Bugzilla 6079 concern). |
| Input and output | `echo pveterm-$((6*7))` printed `pveterm-42`. `uname -sr; tty; echo "TERM=$TERM"` printed `Linux 7.0.0-42-generic`, `/dev/ttyS0` and `TERM=xterm-256color`. |
| Byte transparency | bash's colour prompt, bracketed-paste toggles and systemd's OSC 3008 shell-integration sequences reached the console unchanged. `printf` of `中文` and a 256-colour SGR (`38;5;208`) rendered as sent. Typed `中文 é` came back through readline intact. |
| Resize | The initial `1:100:30:` and a later `1:120:40:` were accepted; the session stayed up. The guest's `stty size` still said `24 80`, as a serial line carries no window size. `stty rows 40 cols 120` in the guest worked (`tput` 120/40), and it was set back to 24x80 afterwards. |
| Detach | Closing the pseudoconsole ended PveTerm. termproxy's task ended with status OK, and the guest's `bash` on `ttyS0` kept running (checked with `ps -t ttyS0` over SSH). |
| Single client | While the human's own terminal client had the serial console open, a second session connected (`starting serial terminal ...`) but got no data: QEMU's socket chardev serves one client at a time. It worked again once the human closed theirs. Worth a line in user docs. |
| Idle without keep-alive | With `--keepalive 0`, the session sat 335 s (5 min 35 s) with no traffic either way. Then `echo idle-end-$((40+2))` printed `idle-end-42`: neither termproxy nor pveproxy on this version enforces the 5-minute timeout the pve-xtermjs README mentions, which matches their sources. Proxies or NAT between client and node may still drop idle connections. |

## Hands-on use by the human (Windows Terminal and herdr)

The human used the bridge interactively on the `ubuntu` guest's serial console, in a bash they had logged in themselves
(TERM=xterm-256color).

- **herdr** (a terminal multiplexer) pane, through `pve-vv.py --term ... --here`, which runs PveTerm in the current console:
  - It connected and worked.
  - htop and apt saw a wrong terminal size. A serial line carries no window size, so the kernel's tty size stays at its
    default.
  - neovim found the right size, probably by asking the terminal itself; its source was not checked. Those queries
    and their answers pass through the bridge unchanged.
- **Windows Terminal**, through `pve-vv.py --term ... -- wt.exe -w new new-tab ... "{exe}" console --pipe "{pipe}"
  --nonce "{nonce}"`:
  - No problems in a first test.
  - After a resize, htop showed the right size.
  - Mouse clicks on htop's items worked, so mouse reporting passes through both ways.
  - This machine's default terminal application is conhost. A plain new console opens there, so a launcher has to call
    `wt.exe` explicitly to use Windows Terminal.
- **Two things the human asked for after this test:**
  - an ssh-style escape: `~.` at the start of a line, with no timeout; the user can opt out;
  - Ctrl+D only ends the guest's shell, and getty then shows the login prompt again, so the bridge never sees the end
    of the session.
- **Also from this use:** `pve-vv.py --ca-from-spiceproxy` pinned the CA from a `spiceproxy` answer, which is the
  cluster's SPICE CA. The API certificate here is publicly trusted and did not verify against it, so the option was
  wrong and has been removed (see the follow-up below).

## Follow-up the same day: Codex review fixes and the input escape

Window-free only (hidden pseudoconsoles and loopback fakes); no VM and no live PVE in this round.

- **Escape (the human's request above, approved 2026-10-30):** `~.` at the start of a line quits, `~~` sends `~`,
  `~?` shows help, no timeout, `--escape none` or `--escape C`. Decision 0036 has the rules. Tests: `EscapeTests`
  (line-start rules, `~~`, `~?`, other keys in order, disabled and custom character, a pasted `"\r~."` quitting as in
  ssh, bracketed-paste content never an escape, 0 B allocation), and PveTerm under a pseudoconsole quitting with `~.`:
  exit code 0, the WebSocket closed with a close frame, console modes and code pages back as before, and only the
  non-escape bytes reaching the fake termproxy. Ctrl+D's behaviour is unchanged: it belongs to the guest.
- **Helper TLS:** `tools/pve-vv.py` now verifies every API request (system roots, or a `PVE_CA_FILE` it also passes on
  to PveTerm to pin). Codex's `TerminalHelpersAuthenticatedApiCallRejectsAnUntrustedServer` checks that no request
  reaches an untrusted loopback server. Not re-run against the live API in this round.
- **Other review fixes,** each with Codex's failing test now passing: the API-stage deadline reports
  `timed out opening the console.`; the hand-off deadline covers the whole exchange on both sides (the bridge closes
  the pipe once it holds the whole descriptor, and the launcher waits for that instead of an uncancellable drain);
  Ctrl+Space reaches the guest as NUL; a pending input send is waited for without allocating.
- **Codex re-review (2026-10-31):** the helper's Python hand-off server got the same 30-second whole-exchange
  deadline while the launched command still runs (`HelperDeadlineCoversAConnectedClientWhileTheLaunchedCommandIsStillRunning`);
  before that, only the managed side had it. A custom escape of `.` or `?` is now refused (N6), and a doubled escape
  character always sends itself. After the second re-review (N7), the helper's pipe steps are overlapped and wait on
  a latched "expired" event, so a deadline that fires before the connect starts is no longer missed
  (`HelperDeadlineCannotBeMissedBeforeConnectStarts`).
