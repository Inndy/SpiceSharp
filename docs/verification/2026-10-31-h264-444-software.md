# Software H.264 4:4:4 decoding: tests and CPU against MJPEG (2026-10-31)

Decision 0037's 2026-10-31 amendment: H.264 streams the hardware decoder refuses (above all spice-server's default
High 4:4:4 Predictive) decode in software with FFmpeg 9.0.2's libavcodec, linked into spicecodec.dll. No guest was
used: this note covers the window-free tests and a bounded benchmark on the development machine. The live check on
win7 is still to be scheduled (end of this note).

Machine: AMD Ryzen AI MAX+ 395 (16 cores, 32 logical processors), Windows 11 IoT Enterprise LTSC 2024, on mains power,
with the human's usual desktop programs open. These are dev-machine numbers: provisional, to be measured again on a
quiet machine.

Both built on the Linux build box with llvm-mingw (LLVM 23.1.4); `verify.py` passes for both (24 exports; KERNEL32,

arm64 `HAVE_NEON 1`; `HAVE_W32THREADS 1`. The size is the H.264 decoder itself, with its DSP functions for every bit
depth and their assembly (FFmpeg has no switch to leave out the high bit depths). The x64 smoke test passed on
Windows with the Linux-built DLLs. The MSYS2 clang64 toolchain on this machine has no `make`, so FFmpeg wasn't built
here (native/README.md).

## Tests

All window-free, against the committed libx264 clips in `tests/fixtures/h264` (see its README; no guest content):

- `Spice.Native.Tests` `H264DecoderTests` (9 tests): every frame of the 4:4:4 and the 4:2:0 clip decodes, and five
  points per frame in flat areas match the source colours, worst channel off by 1 for both (tolerance 6 and 10);
  mirrored rows; the 10-bit 4:4:4 clip decodes but isn't converted; conversion without a picture or with a short buffer
  fails; garbage, forbidden NAL headers, truncated and bit-flipped access units never crash or return "fatal", and
  decoding goes on; 30 frames decoded and converted allocate 0 managed bytes; and the decoder's 3 slice-thread workers
  run 0 cycles in 1.5 s of idle (`QueryThreadCycleTime` on the threads that end when the decoder closes).
- `Spice.Replay.Tests` `SoftwareVideoSessionTests` (9 tests), a fake hardware factory that takes 8-bit 4:2:0 only (as
  the probed DXVA profile) with the real software path: H.264 is advertised when either path decodes it, also after a
  failed hardware probe, and not with software off and no hardware; a 4:4:4 stream starts on the hardware decoder,
  moves to software on its first frame (the hardware decoder never sees a frame), and every frame's picture lands on
  the canvas, top-down and bottom-up; the next stream starts in software; a 4:2:0 stream stays on hardware; with
  software off, a 4:4:4 stream avoids H.264 as before, also when it is turned off mid-session; a 10-bit stream, which
  neither path takes, avoids H.264; a hardware decoder failing before its first picture hands H.264 to software
  without avoiding it, and a software decoder failing the same way avoids it; 30 shown and 30 hidden software frames
  allocate 0 bytes in the session.
- `Spice.Video.Tests` `SoftwareVideoSettingsTests` (7 tests): `softwareVideo` is on by default and in a file written
  before it existed, round-trips, and reads leniently.
- Every window-free test project passed on this branch: Spice.Native.Tests 36, Spice.Replay.Tests 440, Spice.Video.Tests
  54, Spice.Wire.Tests 27, Spice.Diagnostics.Tests 12, Pve.Api.Tests 219, Pve.Term.Tests 115. In two of the first full
  Replay runs `PixelBufferTests.WarmRentAndReturnAllocateNothing` failed; it passes alone and in the next four full runs,
  and is the flaky process-wide pool measurement already noted in docs/reviews/2026-10-31-monitor-inference.md.
  Spice.Viewer.Tests (windows) was not run. The solution builds without warnings and `tools/package.ps1` publishes
  without warnings; its zip is 41.9 MB. By its parts that is about 12.7 MB more than before (the FFmpeg tarball,
  12.0 MB, and the larger DLL, 0.79 MB compressed against well under 0.1 MB); a zip of the base commit wasn't built.

## CPU per frame against MJPEG

Tool: `native/bench/h264bench.c`, built with MSYS2 clang64 (`-O2 -march=x86-64-v3`), run on the DLLs above. Content,
made with the gyan.dev FFmpeg 9.0.2 build installed here (libx264 core 165) as spice-server's x264enc runs (Annex B,
AUD, ultrafast, zerolatency, sliced threads, intra refresh), 4:4:4 at CRF 23, 120 frames at 30 fps:

- `testsrc2`: FFmpeg's moving test pattern (flat colour areas, text, a moving gradient), desktop-like;
- `mandelbrot`: a zooming fractal, detail everywhere, video-like.

```
ffmpeg -f lavfi -i testsrc2=size=1920x1080:rate=30:duration=4 -pix_fmt yuv444p -c:v libx264 -preset ultrafast \
  -tune zerolatency -crf 23 -x264-params aud=1:intra-refresh=1:sliced-threads=1:threads=8 -f h264 testsrc2-1080.h264
h264bench.exe <native/out/win-x64> testsrc2-1080.h264 [--reps 10]
```

The bench decodes the clip once and encodes each picture with libjpeg-turbo (quality 80, 4:2:0, libjpeg's defaults
that spice-server's MJPEG encoder keeps) as the MJPEG input of the same content. Then each configuration decodes the
whole clip 5 times (10 for the second 1080p run); process CPU time (all threads, `GetProcessTimes`) and wall time are
divided by the frames. Decoder creation is outside the timing (0.03-0.05 ms with 1 thread, 0.3-0.4 ms with 4). MJPEG is
`tj3Decompress8` to BGRX, the call the viewer makes. "+BGRA" adds the conversion into the frame buffer, which the viewer
always does for a shown frame; the viewer uses 4 threads on this machine (min(4, logical processors)).

CPU ms per frame (wall ms per frame); two runs per clip, separated by "/":

| Content | Size | KiB/frame H.264 / MJPEG | H.264 1 thread + BGRA | H.264 4 threads + BGRA | MJPEG |
|---|---|---|---|---|---|
| testsrc2 | 1920x1080 | 71.8 / 89.1 | 2.11 / 2.14 (2.11 / 2.11) | 1.77 / 2.50 (1.18 / 1.19) | 1.77 / 1.72 (1.77 / 1.76) |
| testsrc2 | 1600x900 | 53.3 / 74.8 | 1.41 / 1.48 (1.45 / 1.47) | 1.46 / 1.41 (0.85 / 0.86) | 1.30 / 1.33 (1.31 / 1.31) |
| mandelbrot | 1920x1080 | 163.4 / 189.1 | 3.85 / 3.46 (3.95 / 3.50) | 3.46 / 3.80 (1.59 / 1.52) | 2.71 / 2.63 (2.71 / 2.69) |
| mandelbrot | 1600x900 | 121.9 / 141.0 | 2.73 / 2.81 (2.73 / 2.80) | 2.40 / 2.42 (1.17 / 1.19) | 1.95 / 1.95 (1.98 / 1.97) |

A third 1080p testsrc2 run with 10 rounds: H.264 4 threads + BGRA 2.16 CPU (1.25 wall), MJPEG 1.78 (1.80).

Decode alone (no conversion), 4 threads: testsrc2 1.43-1.71 ms at 1080p, 1.04-1.25 ms at 900p; mandelbrot 2.66-3.12 at
1080p, 2.03-2.16 at 900p. The BGRA conversion (one thread, Q14 fixed point, vectorized by clang with AVX2) adds about
0.4-0.6 ms at 1080p and 0.3-0.4 ms at 900p.

Reading:

- Software 4:4:4 H.264 costs about as much CPU per frame as MJPEG of the same picture: from equal to about 1.4 times
  (the run-to-run spread here is up to 20 %). At 30 fps 1080p that is roughly 50-110 ms of CPU per second, a few
  percent of one core, against 50-80 ms for MJPEG.
- Slice threads cut the wall time per frame (latency) to about 40-60 % of one thread, for about the same CPU.
- These clips come from x264's `ultrafast` preset at CRF 23, which compresses little better than MJPEG at quality 80
  (0.8-0.9 times the bytes). spice-server's own rate control sets the H.264 bitrate from the measured bandwidth, so the
  bandwidth saving on a real link was not measured here; neither was the server's encoding CPU. The live check should
  record both.
