Host: Windows 11 IoT Enterprise LTSC 2024, AMD Radeon 8060S, 3840x2160. Guests on Proxmox through spiceproxy:
a Windows 7 SP1 guest (win7) and a Windows 8.1 guest (win81), both `vga: qxl`, `audio0: ich9-intel-hda,driver=spice`,
spice-guest-tools installed (vdagent + QXL driver). Viewer: the portable zip build (Native AOT) unless noted.

## M7: media

- Audio: `playback` channel links; guest system sounds start WASAPI playback (2 ch, 48 kHz, s16, 40 ms device buffer)
  on both guests.
- MJPEG video streaming: verified live on win7 after the human set `spice_enhancements: videostreaming=all` as
  root@pam (Proxmox refuses API tokens for that option, including root's). A double-buffered guest window painting
  bitmaps at ~30 fps became a 480x320 MJPEG stream, and a YouTube video in the guest browser a 1280x720 stream; both
  displayed correctly with 0 dropped frames, and the human confirmed sound and video were good. (A window painting
  solid fills, or one without double buffering, produces fills or short strip streams instead.) Also covered by
  tests/Spice.Replay.Tests/DisplayStreamTests.cs. win81 does not have video streaming enabled.

## Settings and per-VM window state (portable zip build)

- First run created `data\settings.json` and `data\viewer.log` beside the exe; the VM key was
  `<proxy host>|<VM title>`.
- A window moved to (300,200)-(1700,1100) reopened at exactly that rect; a maximized window reopened maximized; the
  "Show guest cursor in server mouse mode" toggle persisted as `serverCursor: "hidden"`.
- Server mouse mode cursor, tested on win81 with the guest agent service stopped (`mouse modes supported=1`,
  `agent=False`): "show guest cursor" on, captured pointer visible (guest shape); toggled off, captured pointer hidden
  (`GetCursorInfo` flags=0) and clipped to the guest image; after Ctrl+Alt+R the clip is released and the pointer is
  visible again on the next move. The agent service was restarted afterwards.
- `--install` / `--uninstall` round trip (the human allowed it on 2026-10-29; baseline: no `.vv` association, no
  install or settings folder): install copied the program to `%LOCALAPPDATA%\Programs\SpiceViewer` and registered
  HKCU `.vv` -> `SpiceViewer.vv` -> the installed exe; opening a fresh .vv through the shell started the installed
  exe, logged to `%LOCALAPPDATA%\SpiceViewer`, deleted the .vv (`delete-this-file=1`) and saved settings to
  `%APPDATA%\SpiceViewer`. `--uninstall` run from the installed copy removed its own folder after exit and the ProgId.
  The first round left an empty `.vv` key with our content type; Unregister now removes our values and the key when
  nothing else uses it, and a second round left no registry trace. The install dialog cut long paths with an ellipsis;
  dialogs now size to their content. The test's settings folder was deleted afterwards.

## Allocation profile of the hot paths

Native AOT doesn't emit .NET runtime ETW events, so the JIT build of the same code was profiled with
`Microsoft-Windows-DotNETRuntime` GC keyword at verbose level (GCAllocationTick roughly every 100 KB) while the
guest repainted a 640x400 window ~30 times a second, played audio, and the host pointer swept the viewer at ~125 Hz.

- Before: each idle-to-busy `SpiceChannel.Send` queued a thread-pool work item and a new async writer Task (seen as
  `<WriteLoopAsync>d__35`), i.e. allocations on the input path. Fixed: one long-lived writer loop per channel parks on
  a reusable `IValueTaskSource`; the async-writer allocation no longer appears.
- Remaining small-object allocations under that load (~5 samples per 25 s, about 20 KB/s): `CursorShape` and its
  `uint[]` pixels, decoded whenever the guest sends a new cursor shape (the sweep changes the guest cursor often).
  This is the "cursor shape change" control path the allocation decision allows.
- Large-object `byte[]` of 2-4 MiB, about 3 per 25 s: Codex task 11 traced these to ArrayPool growth for decoded
  images (`DecodedImage` pixel rents of new size classes); a warmed replay allocates none.
- Deterministic replay (Codex task 11, second pass after warm-up): before the fixes each decoded draw allocated 88 B
  (the `DecodedImage` wrapper plus a formatted statistics key) and each cache hit 56 B. After pooling the wrappers and
  precomputing the keys, all four fixtures allocate only their surface buffers (win7-rich: 1,929 messages,
  1,920,072 B = 1,920,000 B of pixels + the surface object) and 10,000 cache hits allocate 0 B. The bound in
  `AllocationTests` is now surface payload + 4 KiB.
