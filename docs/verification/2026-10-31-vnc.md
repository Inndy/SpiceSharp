# VNC bridge against a live Proxmox VNC console (2026-10-31)

Checks of `PveTerm vnc` ([decision 0043](../decisions/0043-vnc-consoles-bridge-to-the-users-vnc-viewer.md)) against the
`ubuntu` guest's VNC display on the PVE node, through `vncproxy` and `vncwebsocket`.

Method: headless only. No VNC viewer window was opened. The viewer side was `tools/vnc-probe.py`, a small RFB client
that prints what the server sends and sends the guest no input. It was started as the bridge's custom viewer command:

```sh
python tools/pve-vv.py --vnc VMID --here -- python -I tools/vnc-probe.py {port}
python tools/pve-vv.py --vnc VMID --here --keepalive 0 -- python -I tools/vnc-probe.py {port} --hold 960
```

The API token stayed inside `pve-vv.py` and the descriptor pipe. PveTerm requested the session itself, and no
ticket or password was printed. The guest uses qxl, so it has SPICE too: Proxmox gives every VM a VNC server
(`-vnc unix:...,password=on`) unless its display is `serialN` or `none`. VNC and SPICE are separate QEMU servers.
`vncproxy` sets only the VNC password, so it does not touch SPICE. The human's SPICE session was not watched during
these runs.

## Handshake and what the server offered

| Step | Seen |
|---|---|
| Upstream | `vncproxy` with `websocket=1` answered a one-time 8-character password and a 59xx port. The `vncwebsocket` upgrade succeeded with the token. QEMU sent `RFB 003.008` and offered only security type 2 (VNC authentication). The DES response with the password was accepted. |
| Local | The bridge offered the probe RFB 3.8 with security type None (`[1]`). The probe connected from the same user and integrity level, so the peer check passed. |
| ClientInit | The probe sent shared=1, which the bridge forwarded (it forwards shared=1 whatever the viewer asks; the loopback tests cover an exclusive request). No other client of that VM was disconnected. Corrected 2026-10-31 after review: this row first said the probe sent 0. |
| ServerInit | 1600x900, 32 bpp, depth 24, little-endian, true colour, max 255/255/255, shifts 16/8/0. The name is QEMU's (`QEMU (<guest name>)`). ServerInit arrived 0.56 s after the probe connected. |
| Unsolicited, after SetEncodings | ExtendedClipboard capabilities (ServerCutText with length −8). QEMU ExtendedKeyEvent acknowledgement (pseudo-encoding −258). PointerTypeChange absolute. LEDState 0. AlphaCursor 64x64 with hotspot 4,4. ExtendedDesktopSize with 1 screen. |
| First update | One ZRLE rectangle 1600x900, 91,409 compressed bytes, 0.63 s after connect. |
| End | The probe closed. PveTerm printed `Session ended: the VNC viewer closed the connection` and exited 0, and `pve-vv.py` reported the hand-off as served. |

The ExtendedKeyEvent acknowledgement is what a viewer with QEMU extended key events (TigerVNC) needs to send scan
codes. Viewers without it send keysyms, which QEMU maps through its keymap.

## Idle: Proxmox's 15-minute limit and the keep-alive

`qm vncproxy` exits after 15 minutes without traffic. Two runs held the probe idle for 960 s (16 minutes), with no
input and an unchanging screen.

| Run | Result |
|---|---|
| `--keepalive 0` (control) | At about 15 minutes: `Session ended: the VNC server closed the connection`. The probe's socket was aborted. |
| Default keep-alive (600 s) | The bridge is due to send one incremental FramebufferUpdateRequest after 600 s idle, between two viewer messages. The session was still up at 960 s, and the next update arrived. |

Between those wake-ups the bridge has no timer. It has one pending delay until the next keep-alive is due, and
traffic in either direction moves that point later.
