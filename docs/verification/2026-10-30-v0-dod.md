## Method

- **Idle measurement** (`measure.ps1`, scratch): 60 s windows, the viewer windowed (not minimized), focused with the
  keyboard hook installed, host pointer parked outside it. Per window:
  - CPU: `QueryProcessCycleTime` delta. `Process.TotalProcessorTime` was also read, but it moves in 15.6 ms ticks and
    showed 0 or 1–2 ticks, so the cycle count is the number to read. "ms" below = cycles / 3 GHz, an estimate.
  - GPU: the `RunningTime` delta of every `GPU Engine` instance of the process (WMI raw counters, 100 ns units).
  - Wakeups: `ContextSwitchesPersec` raw deltas per thread ID (threads that exited in the window aren't counted).
  - I/O: `Win32_Process` read/write/other operation and byte deltas.
  - Presents: in-box ETW (`logman`, Microsoft-Windows-DXGI), `Present` events of the process.
- **Static guest:** no screen saver is configured on either guest (`ScreenSaveActive=1` but no `SCRNSAVE.EXE`), the
  win81 display never turns off (AC timeout 0), no animated windows were open (a minimized PowerShell window on win81),
  and both taskbar clocks show minutes only. Nothing was changed in the guests for this: the clock's minute change is
  the only update, and it shows up as one present per minute (at :02–:03 of each minute in the traces).
- **Media for the "after playback" runs:** on win81 a 20 s guest window painting photo-like bitmaps (image draws; win81
  doesn't stream) plus three system sounds (three playback streams); on win7 a 25 s animation that spice-server sent as
  a 480x320 MJPEG stream (`stream 45 ended after 514 frames, 0 dropped, 0 hidden by its clip`) plus four system
  sounds. Guest scripts ran in the interactive session through scheduled tasks over WinRM. Measurement started 25–30 s
  after the stream ended.
- **Startup timing** (`perf.ps1`): 5 runs per guest, the `.vv` fetched before the clock starts, `Start-Process`, then an
  external watch for the process's first visible window (2 ms sleeps) and the viewer's own log lines (`Main reached N ms
  after process start`, `window shown N ms after start`, `first frame N ms after start`). "From process start" = Main
  offset + the logged time. Warm file cache.
- **Latency** (`latency.ps1`, `latan.py`): ETW with Microsoft-Windows-DXGI and Microsoft-Windows-Winsock-AFD (the kernel
  network provider needs elevation; AFD doesn't). Input: 100 absolute pointer moves over the viewer 50 ms apart, injected
  with `SendInput`; time from each move to the viewer's next `AfdSend` on the inputs channel's socket (one send per move).
  Display: the guest animation on win81 (223 presents); the display socket's receive calls grouped into bursts (gaps
  > 4 ms), each burst to the next `Present` start. Moving the pointer over the window caused 0 presents.
- **Keyboard** (`kb.ps1`): keys injected with `SendInput`, scan codes filled in. `KeyboardHook.HookProc` doesn't look at
  `LLKHF_INJECTED`, so injected keys take the same path as physical ones (checked in the source before relying on it).
  Inside win7 a low-level keyboard hook in the interactive session logged every key event the guest received, and at the
  end the guest's async state of the modifier keys. Host state from `GetAsyncKeyState` and the foreground window.
  Focus loss: LShift, RCtrl and Q held, then a mouse click on a separate host window, then the keys released.
- **Expired ticket:** `.vv` files opened with the viewer, the dialog read with UI Automation and captured.

- The limit is 0.5% CPU averaged over 60 s, i.e. 300 ms of one core's time (or 0.5% of all 32 CPUs, 9.6 s). The
  largest window used about 8.5 ms. GPU running time stayed at or below 0.18 ms per minute (the minute-clock present's
  copy), and no Video engine was used. Disk I/O was 0 bytes; "other" I/O operations were 9–13 per minute.
- Audio streams opened and closed with each sound (`Audio: playing …` / `stream closed; underruns 0 …`; one underrun
  on the first win81 stream, as F4 of [2026-10-30-live-options.md](2026-10-30-live-options.md)).
- The first minute after playback on win81 had 9.8 wakeups/s and 3.7× the cycles of the next; two threads exited in
  that window (thread-pool workers retiring after the burst). The minute after was back to the connect baseline.

### M8: software rendering

The software profile exists (spec "Software rendering", decision 0017): the presenter falls back to WARP when the
hardware device fails, and `DXGI_ADAPTER_FLAG_SOFTWARE`, vendor 0x1414 or `SPICEVIEWER_FORCE_WARP=1` select 1:1 only and
a 34 ms minimum present interval; v0 advertises MJPEG only in every profile. Run with `SPICEVIEWER_FORCE_WARP=1` on
win81:

- Log: `hardware device skipped (SPICEVIEWER_FORCE_WARP), using WARP`, `adapter 'Microsoft Basic Render Driver'
  software=True level=D3D_FEATURE_LEVEL_11_0`, first frame 242 ms after start, direct path 1616x1044.
- Picture correct (screenshot); window menu: "Fit to window" greyed, "1:1 pixels" checked.
- Guest animation (12 s): 258 presents, at most 22 per second (the guest's rate), intervals 30.0 ms minimum (47 ms
  median); the same animation on the hardware path had a 7.9 ms minimum. Viewer CPU over those 16 s: about 94 ms.
- Idle: see the table above (8.3 M cycles, 0 GPU, 1 present).

This is the profile on a GPU machine; the matrix's "client VM with only WARP" and the RDP check remain open (K4).

## Findings

- **K1: an idle session keeps the memory its busy period grew.** After 20 s of image draws and three sounds on win81,
  private bytes went from 79.5 MB to 180.7 MB and stayed there over the next two idle minutes (working set 98 → 196 MB).
  On win7 a 25 s MJPEG stream plus sounds took it from 65.8 to 86.4 MB. The forced-WARP session used 32.7 MB private
  at idle (25 threads, against 52 on the AMD device), so about 45 MB of the hardware baseline belongs to the GPU driver.
  Principles §2 asks to release what an idle session doesn't use; where the 100 MB sits (ArrayPool, GC heap, decode
  buffers, driver) was not measured. Not a DoD criterion.
- **K2: an "already used" `.vv` still connects while its ticket is valid.** spiceproxy accepted the same `.vv` a second
  time 15 s later; only expiry produced the dialog. The viewer can't tell the two cases apart, so the DoD's "expired
  `.vv`" passes; users reopening a `.vv` within the ticket's lifetime simply connect.
- **K3: Task Manager's power-usage column was not read.** Task Manager auto-elevates on this host (UAC
  `ConsentPromptBehaviorAdmin=5`, a medium-integrity session), so UI Automation from this session can't read it and the
  window couldn't be closed afterwards; it was not opened. Every input of that column was measured instead (CPU, GPU,
  disk, network above), all near zero. The human can confirm "Very low" by eye.
- **K4: WARP checked only through the debug switch.** The software profile was exercised with
  `SPICEVIEWER_FORCE_WARP=1` on a GPU host. A client VM that has only WARP (or Basic Display) and the RDP session are
  still open for M8. The 30 presents/s cap wasn't the limiting factor here (the guest sent ~21 frames/s); the observed
  minimum interval was 30.0 ms where the code waits for 34 ms, since `Environment.TickCount64` moves in 15.6 ms steps.
- **K5: hotkeys let their modifiers reach the guest for a moment.** For Ctrl+Alt+R the guest saw Ctrl down, Alt down and
  both up 2–40 ms later; for Shift+F11 it saw Shift down and up, then a second Shift key-up (the physical release
  arriving after the viewer had already released it). The modifiers are sent before the hotkey's last key is known, and
  `CancelGuestInput`/`ReleaseAllKeys` let go of them, so nothing stays down. A guest bound to a modifier-only press
  (e.g. an IME switch on Ctrl+Shift) could react; nothing did on win7.
