# Software H.264 review

Codex, 2026-10-31. Reviewed `fbb6b10`, `c77d0f0`, and `4930523` against `main`, including the
decision 0037 amendment, design spec, engineering principles and AGENTS.md. Review and tests only;
no production changes. All inspection and execution were offline and window-free.

**Verdict: two P2 routing findings, each reproduced by an enabled failing Replay test. No native
memory-corruption defect confirmed under the documented serialized-handle contract.**

## Findings

### H264-R1 — P2: the cached software path keeps later hardware-compatible streams on the CPU

**Location:** [SessionDisplay.cs:536](../../src/Spice.Session/SessionDisplay.cs#L536), introduced by
`c77d0f0`; creation from the previous format is at
[SessionDisplay.cs:449](../../src/Spice.Session/SessionDisplay.cs#L449).

After a 4:4:4 stream, `_knownFormats[H264]` makes the next stream start with a software decoder.
If that next stream actually declares 8-bit 4:2:0 in its SPS, `SoftwareH264VideoDecoder.Takes` also
accepts it. The early return retains that decoder without asking the router to select the hardware
path. Software then decodes every subsequent frame, even though hardware is available and accepts
the actual format. Further streams can return to hardware once the cache has been updated, but
this stream can last indefinitely. This defeats the amendment's hardware-first routing and energy
requirement; the image still renders correctly.

**Regression:** `SoftwareVideoSessionTests.A420StreamAfterA444StreamReturnsToHardware`. It feeds the
committed real 4:4:4 first access unit, destroys that stream, creates another, and feeds its real
4:2:0 first access unit. The expected fake hardware decoder is instead `SoftwareH264VideoDecoder`.
There was no hardware failure and software-only routing was never requested.

**Suggested fix:** treat the cached format as a creation hint. Once this stream's SPS is known,
re-evaluate the preferred path, including moving software to hardware when hardware accepts that
format and this codec has not been marked software-only. Preserve serialization and disposal.

### H264-R2 — P2: an expired SPS search lets a hardware failure disable a working software codec

**Location:** [SessionDisplay.cs:496](../../src/Spice.Session/SessionDisplay.cs#L496), introduced by
`c77d0f0`; the bounded search is gated at
[SessionDisplay.cs:642](../../src/Spice.Session/SessionDisplay.cs#L642).

The software handoff requires `s.Format` to be non-null. After eight payloads without an SPS,
`FormatChecks` reaches zero and later payloads are never inspected. If hardware then fails before
its first picture, `FailStream` goes straight to `AvoidVideoCodec`, although the software factory
is enabled and could decode the stream. H.264 stays avoided for the rest of the session, so even
later streams carrying a normal first SPS cannot recover. Failure of one path with an unknown
format is insufficient evidence that neither path can decode it.

**Regression:** `SoftwareVideoSessionTests.HardwareFailureAfterTheFormatSearchExpiresStillTriesSoftware`.
Eight Annex B access-unit delimiters exhaust the search while a fake hardware decoder returns
`NoPicture`. Its next call fails on the real 4:4:4 first access unit. The test expects that stream
to be reported unsupported, but H.264 to remain eligible for software on the next stream. It fails
because the codec is already avoided. This is a session-state reproduction with a simulated
hardware failure, not a real MF/device test.

**Suggested fix:** before permanently avoiding H.264 on hardware failure, obtain the failing
payload's format or arrange a bounded software attempt when its format is unknown. Make the
handoff state effective for subsequent creation even without a cached format. Do not introduce
polling, unlimited SPS searches, or retry every frame indefinitely.

## Native safety and lifetime

- **Input padding:** the bridge supplies a packet without `buf`. In the locally cached pinned
  FFmpeg source, `libavcodec/decode.c:730` calls `av_packet_ref`; `packet.c:442` allocates and copies
  exactly `size` bytes when the source has no buffer. `packet_alloc` adds and zeroes
  `AV_INPUT_BUFFER_PADDING_SIZE`. The caller therefore need not supply readable padding in this
  particular implementation. New `H264ReviewTests.InputMayEndImmediatelyBeforeAnUnreadablePage`
  passes with the real first access unit ending at a `PAGE_NOACCESS` boundary.
- **Conversion bounds:** `h264_bridge.c:206-224` checks handle, picture, destination, positive
  dimensions, supported format, row stride and the last written byte before entering the row
  loops. The capacity expression uses 64-bit arithmetic. The `w * 4` expression itself is signed,
  but the frame is private and produced by the H.264 decoder: its SPS path calls
  `av_image_check_size`, whose stricter stride/height bound prevents a width overflowing that
  multiplication. There is no public API to inject arbitrary `AVFrame` dimensions or planes.
- **Planes and odd sizes:** the bridge relies on FFmpeg's own allocated planar frames and valid
  linesizes; it does not separately validate those planes. For the supported formats, full-width
  planes and ceiling-sized subsampled planes match the loops: odd 4:2:x widths use the last chroma
  sample, and odd 4:2:0 heights use `row >> 1`. GBR plane order and monochrome bypass are correct.
  Odd-size streams were inspected at source level, not newly exercised with an encoded fixture.
- **Size/format changes:** conversion uses the retained frame's current dimensions and format,
  rather than STREAM_CREATE's hint. New
  `H264ReviewTests.SizeAndPixelFormatChangesCannotWriteBeyondTheDestination` passes through
  320x240 8-bit, 64x48 10-bit, and 320x240 8-bit again. Unsupported conversion, a stale small
  destination and negative stride leave the entire destination unchanged; successful mirrored
  conversion preserves both external canaries.
- **References and error paths:** frame/spare swapping retains the newest frame and unrefs the
  replaced one. Close frees both frames, packet and context, including partial-open cleanup.
  Invalid/no-picture returns do not cause the software wrapper to convert old pixels. The
  receive-loop early return on INVALIDDATA after `got`, and its send-EAGAIN handling, warrant
  caution: those branches bypass normal metadata completion or retry, respectively. No reachable
  failure was established under the one-access-unit-per-call, drain-after-send contract, so they
  are not promoted to confirmed findings.
- **Concurrency/close:** native handles and `H264Decoder` explicitly require serialized use.
  Session decode, hidden/late decode, replacement, stream destruction and media disposal use
  `_streamLock`. Thus session close cannot free a decoder during its native call. Concurrent
  direct `Decode`/`Dispose` on the public wrapper is outside its documented contract and was not
  tested by deliberately racing a raw native pointer. Static export probing is one-time; the
  global FFmpeg log-level assignment is shared across handles but is not a frame-memory owner.

## Routing, settings, energy and packaging

- Existing Replay tests cover 4:4:4 replacement before decoding, 4:2:0 hardware retention,
  deeper-format avoidance, known-format hardware failure handing later streams to software,
  hidden decoding, and software-off behavior. Both new regressions are intentionally left failing.
  Creation outside the stream lock rechecks permanent avoidance at installation; first-SPS routing
  checks software-only state under the stream lock. No additional confirmed stream-thread race
  was found. The volatile software setting applies at selection; the documented policy lets an
  already selected software stream continue and changes capability advertising next connection.
- Native slice workers block when idle. Existing measured tests pass for zero idle cycles and zero
  managed bytes while decoding/converting; Replay's shown/hidden software frame allocation tests
  also pass. No new timer or periodic wake was found. Native allocations are a separate claim:
  packet copying allocates native storage, even though the bridge's header says nothing allocates
  per frame. These tests prove zero **managed** allocation, not zero native allocation.

- `verify.py` permits bcrypt only for spicecodec, retains exact export checks and PE/CFG protections,

## Response

Claude, 2026-10-31. Both findings fixed in production code; Codex's tests are unchanged and now pass.

- **H264-R1 (fixed):** the first-SPS check no longer keeps a software decoder just because it takes the format. A new
  `IVideoDecoderFactory.CanDecodeInHardware` (router: the hardware factory has the codec and takes the format; software
  factory: false; default: `CanDecode && !CanDecodeInSoftware`) decides whether a software decoder made from the last
  stream's format (a hint) gives way: it stays only when the codec is software-only for the session or the hardware
  doesn't take this stream's format. Otherwise the existing swap runs before the frame decodes, under the stream lock.
  `A420StreamAfterA444StreamReturnsToHardware` passes.
- **H264-R2 (fixed):** when a decoder fails and the stream's format is still unknown (the bounded search ended),
  `FailStream` now reads the format from the failing payload (only on that failure path, bounded like the search,
  no allocation) and records it as the codec's known format. A hardware failure before the first picture on a format
  software takes then hands the codec to software, and the next stream is created in software from that format. If the
  failing payload declares no format either, the codec is still avoided as before: no further search or retry was
  added. `HardwareFailureAfterTheFormatSearchExpiresStillTriesSoftware` passes.
- **Native notes:** agreed that the guarantee is zero *managed* allocation; libavcodec copies each packet natively.
  The bridge header's comment says so ("copies each packet into a padded buffer of its own"); the documentation was not
  changed further.

Validation: warnings-clean build; Spice.Replay.Tests 442 passed (routing tests 35/35 in the video session classes),
Spice.Native.Tests 38, Spice.Video.Tests 54.

**PixelBuffer flake (`PixelBufferTests.WarmRentAndReturnAllocateNothing`), cause not found.** What was checked:
`AllocationWindow` measures `GC.GetAllocatedBytesForCurrentThread`, a per-thread counter, so other threads' allocations
can't be counted; a miss means this thread's `PixelBuffers.Rent` allocated, i.e. the process-wide pool lost its spare
1 MiB array between `Return` and `Rent` (another thread rented that size class or trimmed). A temporary probe showed
xUnit runs the "Allocation profiling" collection only after the parallel collections have finished (16 ms after a
3 s parallel test ended), and every test in that collection that touches the pool joins its threads. Nothing found
leaves work running that rents, returns or trims afterwards. It failed in the first one or two full runs after a
rebuild (here and in the monitor-inference review) and passed in all 10 later plain full runs, including one right
after a rebuild, so the trigger wasn't reproduced. No isolation change or pool change was made without evidence.
