## R1 - P3: Give wrapped message-image text its measured height

Location: `src/SpiceViewer/MainWindow.Session.cs:389-402` (`b8b5424`).

The new renderer measures the body, then caps its rectangle at `ah / 50 + ah / 12`. At 320x240 that is only
24 pixels, and at 320x180 it is 18 pixels. The shipped network-error reason needs 30 pixels (two lines) in
the selected 12-pixel Segoe UI font. With the newly added `DT_EDITCONTROL`, the last incomplete line is
omitted entirely: the last painted pixel is only 14 pixels below the body's top in both cases. Adding the
detail underneath does not restore the missing reason text. This affects the image used after the guest
blanks and the overlay on a small guest surface; the pre-frame GDI status has a separate layout.

The regression calls the actual compiled `DrawText` on an uninitialized MainWindow object and examines its
BGRA output, using a separate memory DC to measure the complete text. Empty title/detail isolate the body's
pixels. The 800x480 control passes. No HWND, presenter, screenshot or golden image is involved.

Lay out the title, complete measured body and detail together, reserving room for Close when applicable.
Moving detail below the capped body is insufficient. **Provenance:** the fixed vertical budget predates this
branch; this change retains that limitation and adds EDITCONTROL, which suppresses the incomplete line rather
than painting its visible portion. This is a remaining layout defect in the touched renderer, not a newly
introduced failure of ordinary pre-frame word wrapping.

Failing tests: `StatusLayoutReviewTests.MessageImageKeepsEveryWrappedReasonLine(320, 240)` and `(320, 180)`.

## R2 - P3: Observe failed and incomplete WriteFile results

Location: `src/SpiceViewer/LogFile.cs:58-59` (`611a594`).

`WriteLine` ignores both WriteFile's success result and the returned byte count. An actual failed append is
therefore reported as a successful void return. A temporary log with another handle holding a byte-range lock
reproduces this: the attempted line writes zero bytes, no IOException is raised, and after unlocking a later
line is written normally. The first line has permanently disappeared. The former StreamWriter/FileStream path
reported write failures; replacing it with an unchecked native call loses that signal.

Check the native result and byte count and surface failure to the logging policy. Preserve the single-call
whole-line property: retrying only a missing suffix could interleave with another viewer. The test expects an
IOException from this low-level writer; any separate best-effort application policy should be explicit.
Only the byte-range-lock failure is reproduced here; disk-full and partial-success cases were not simulated.

Failing test: `LogFileReviewTests.AFailedAppendReportsTheErrorInsteadOfClaimingSuccess`.

## R3 - P3: Keep the SafeFileHandle alive and serialize disposal with writes

Locations: `src/SpiceViewer/LogFile.cs:51-63` (`611a594`).

WriteLine uses the raw value from `DangerousGetHandle`, with neither a SafeHandle reference held through the
native call nor disposal coordinated by `_gate`. Dispose can close the handle after it is fetched and before
WriteFile consumes it. A recycled handle value can then address another object. A simpler deterministic
boundary test already fails: Dispose followed by WriteLine returns successfully instead of rejecting the
closed writer. Checking only WriteFile's error result is insufficient for the concurrent handle-reuse race.

Serialize disposal and writing, reject writes after disposal, and protect the SafeHandle through the unmanaged
call (for example, a balanced DangerousAddRef/DangerousRelease). Keep this allocation-free after warm-up.
**Scope:** Program.SetupLog roots the logger in the process-wide sink and currently never disposes it. This
is a defect in the new disposable writer's lifetime contract, not a reproduced normal viewer-shutdown failure.
The test proves the closed-writer behavior; concurrent handle reuse/corruption was not exercised.

Failing test: `LogFileReviewTests.ADisposedLogCannotPassItsClosedHandleToWriteFile`.

## Other correctness checks

- **Append and truncation (0040):** CreateFile requests FILE_APPEND_DATA and SYNCHRONIZE, without FILE_WRITE_DATA,
  uses OPEN_ALWAYS and shares read/write/delete. UTF-8 bytes plus CRLF are issued in one synchronous WriteFile;
  `_gate` protects the reused encoding buffer across callers. The existing three LogFileTests are linked into
  the window-free project and pass: alternating handles, concurrent writers, and in-place truncation with an
  already-open writer subsequently appending at the new EOF. The threshold is strictly greater than 1 MiB at
  startup, not a continuous size limit. The truncate handle shares write access and IOException falls back to
  appending. The two-startup truncate race and consequent loss of intervening lines are expressly accepted in
  decision 0040, so are not a new finding. Simultaneous truncation and an in-flight write were not stress-tested.
- **Status wrapping:** PaintStatus uses the same measured wrapping flags for layout and drawing, measures reason
  and detail separately, centers their combined height, and moves the block above Close when it fits. It uses
  the selected DPI font and recomputes on paint. The production MeasureText control with a 120-character unbroken
  title passes. Extremely long text can still exhaust vertical room; no scroll/overflow policy is specified.
- **Close placement:** Production CloseButtonTop checks pass for client 320x240 at 144/192 DPI and 296x183 at
  144 DPI, including the full scaled button height. These are arithmetic checks, not live DPI-transition or
  text/button-overlap validation. The image renderer positions text in guest/image coordinates while Close is
  a client-space control, so these checks do not certify every scaling mode.
- **L14 wiring (0035):** OnDisconnected obtains reason/detail once, removes an identical detail, and leaves null
  absent. DrawDisconnectedOverlay passes it to the dimmed primary-area image or ShowMessage; ShowMessage stores
  it and passes it to the pre-frame status or RenderMessage. DrawText uses a smaller, dimmer detail font and
  releases it after restoring the previous font. GDI status uses the existing status font with a dimmer color,
  consistent with the record's separate pre-frame wording. Primary-display recovery and graphics failure clear
  the stored message detail. No dropped channel-detail argument was found. No disconnect was triggered here.
- **AOT/native calls:** The production additions use CsWin32 with `allowMarshaling: false`; no handwritten
  DllImport, reflection, dynamic code or serialization was added. The build is warning-free. Test-only reflection
  runs under the JIT, and new handwritten test native calls use LibraryImport. This run did not republish AOT.
- **Energy/allocation:** No timers, polling, periodic flushes or periodic truncation were added. PaintStatus uses
  stack rectangles and fixed string pointers. The log encoding buffer is reused and grows only for a longer line;
  sink string interpolation predates this branch. Message image allocation and GDI font creation happen at state
  changes and completed resizes, not per guest draw/input/audio message. No new hot-path allocation was found by
  inspection; no ETW, idle-energy measurement or allocation benchmark was run.
- **Verification commit:** ee8b40e records the implementer's actual small-window/channel-close/multi-viewer checks.
  Those observations are not independent validation by this review and do not cover the error/lifetime cases above.

## Response

Claude, 2026-10-31. All three findings fixed in production code; no review test was changed.

- **R1:** `DrawText` (the 7-argument signature the test calls) now forwards to `DrawTextBlock`, which measures the
  title, the whole wrapped body and the detail first and draws each in a rectangle of its full measured height, so
  DT_EDITCONTROL has no partial line to drop. The block keeps its old place (title ending just above the centre,
  body starting just below it) and moves up as one when its end would pass a bottom limit, never above the area's
  top. The limit is the area's bottom, or the Close button where there is one: in the message image it is the
  button's client position scaled to the image; on the dimmed frame, the button's current position mapped through
  the guest rectangle to surface pixels (the overlay is drawn once, so after a later resize it scales with the frame
  while the button keeps its DPI offset, as before). Rendered off-window at 320x240, 320x180 and 800x480 with a
  two-line reason and a detail: every line drawn, all above the reserved line.
- **R2:** `WriteLine` checks WriteFile's result and the byte count. A failure throws an `IOException` carrying the
  Win32 message and HRESULT; a short write throws too. Neither is retried, so a line still goes out in one call or
  not at all. The viewer's policy is explicit in `Program.WriteLogLine`: best effort, the sink catches
  `IOException` and `ObjectDisposedException`, drops and counts the line, and after the next line that is written
  adds a `Warn` line "log: N earlier line(s) could not be written". Logging never throws into a session or UI thread.
  Opening the log still fails silently into "no log", as before.
- **R3:** `_gate` now serializes `Dispose` with writes; `WriteLine` throws `ObjectDisposedException` once disposed,
  and holds a `DangerousAddRef`/`DangerousRelease` reference across the native call. No allocation was added on the
  success path (the failure path allocates its exception).
- Decision 0040 records the failure policy and the lifetime rules.
