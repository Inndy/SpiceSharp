## N1 - P1: Apply the PVE TLS policy before the helper sends credentials

Locations: `tools/pve-vv.py:26-32`, newly used by `--term-probe` and `term_main` at `:126-135`.

The C# connector correctly rejects an untrusted endpoint, but the new terminal entry paths first use the helper's
global `ssl._create_unverified_context()`. An ordinary qemu/lxc launch resolves its node with an authenticated API
query; `--prefetch` also requests the session there. `--ca-from-spiceproxy` obtains its supposed pinned CA over the
same unverified connection. Thus the API token can already have been sent to an untrusted endpoint before PveTerm
applies decision 0033. Verifying it later cannot recover the credential or authenticate a CA obtained this way.

The insecure helper primitive predates the commit and its dev-only bypass is disclosed in the docstring. This
finding concerns extending that bypass into the new terminal launch/probe and CA hand-off paths; it is not attributed
as newly invented TLS code. The dev label does not supply the CA-or-system-root validation that 0033 specifies.

Confirmed by extracting only the real helper's `ctx` assignment and `call` function, supplying synthetic credentials,
and calling a loopback HTTPS fake whose CA is not trusted. The fake receives an authenticated POST. The existing C#
TLS controls against the same test PKI instead reject the endpoint before any HTTP request. No real credential file
is executed or read by this probe.

Use the supplied CA or normal system validation for every authenticated terminal-helper request, including any
bootstrap request. An insecure development override, if wanted, needs an explicit separate choice rather than being
implicit in the otherwise verified terminal flow.

Failing test: `PveTermReviewTests.TerminalHelpersAuthenticatedApiCallRejectsAnUntrustedServer`.

## N2 - P2: Convert the API-stage deadline into the documented connection failure

Location: `src/Pve.Term/TermproxyConnector.cs:27-30`, outside the timeout catch at `:48-52`;
caller: `src/PveTerm/Program.cs:53-58`.

The internal 20-second deadline covers the API request, but RequestSessionAsync is awaited before entering the
try/catch that converts an internal cancellation to TermConnectException. If the API/TLS stage stalls, ConnectAsync
therefore throws TaskCanceledException. Program catches only TermConnectException/TermDescriptorException, so this
ordinary connection failure escapes Main instead of printing the controlled failure and returning exit code 1.
The later WebSocket-stage timeout has the conversion; the earlier stage needs the same handling while retaining
normal propagation of a caller's explicit cancellation.

Confirmed with an accepted loopback TCP connection whose peer does not complete TLS. With no caller cancellation,
the internal deadline fires after about 20 seconds and yields TaskCanceledException rather than TermConnectException.
This test uses an event-driven wait, not traffic generation or CPU load.

Failing test: `PveTermReviewTests.ApiStageDeadlineIsReportedAsAConnectFailure`.

## N3 - P2: Make hand-off deadlines cover the connected transfer and drain

Locations: `src/Pve.Term/Handoff.cs:125` and `:170-196`. The Python hand-off at `tools/pve-vv.py:185-204` also
uses unbounded blocking connect/read/drain operations; its new join is not an I/O deadline.

The managed server's timeout and cancellation do not cover synchronous WaitForPipeDrain. A client can submit the
correct nonce and then stop reading; the descriptor fits the pipe buffer, the server enters the drain, and the
handoff never finishes on its deadline. The managed client likewise applies its timeout only to Connect: once a
same-user server accepts the pipe, its synchronous nonce write and descriptor-read loop have no deadline. A stalled
launcher can leave PveTerm waiting forever. These are lifecycle failures even without an adversarial client/server.

Both directions reproduce with local, same-user pipes and a 150-ms production timeout: the operation is still pending
after a two-second test deadline. Closing the peer releases it during test cleanup. The first test uses a two-byte
descriptor, so this is specifically the uncancellable drain, not merely filling a large buffer. The second server
reads the entire nonce before stalling, proving the connection phase already succeeded.

Use one bounded lifetime for connect, nonce, descriptor and any acknowledgement/drain. A wrapper-process exit can be
different from a terminal-process exit (see the coordinator fix below), but neither should defeat an explicit hand-off
deadline. The probes do not require retrying or serving a descriptor to a second client.

Failing tests:

- `PveTermReviewTests.HandoffServerDeadlineCoversAClientThatStopsReadingAfterItsNonce`.
- `PveTermReviewTests.HandoffClientDeadlineCoversAConnectedServerThatNeverWritesTheDescriptor`.

## N4 - P2: Distinguish a valid NUL key from non-character key events

Location: `src/PveTerm/ConsoleFrontEnd.cs:160`.

RunInput unconditionally drops every key whose UnicodeChar is zero. Ctrl+Space/Ctrl+@ use the NUL control character,
so this also drops meaningful terminal input, including the usual Emacs/readline mark command and applications
configured to use that control key. The terminal cannot send it even though UTF-8 encoding and termproxy data framing
can both carry byte 0. Modifier-only events do need filtering; testing only the character value conflates the two.

Confirmed through a hidden pseudoconsole using a Windows Terminal Win32-input-mode Ctrl+Space record followed by
`x`. A separate reader, using the same raw VT input flags, observes a zero-character key-down. The real PveTerm process
then sends only `[120]` to the fake pty, rather than `[0,120]`, and exits normally after the test sends `exit`.
The passing control waits for a final output marker before inspecting its transcript; it does not race the output reader.
No physical keyboard event or input to another process's console is injected.

Failing test: `PveTermReviewTests.ConsoleNulInputReachesTheGuestBeforeTheFollowingKey`.
Passing control: `PveTermReviewTests.NulControlProvesTheConsoleDeliversAZeroCharacterKeyEvent`.

## N5 - P2: Keep the pending-send wait allocation-free too

Location: `src/PveTerm/Bridge.cs:58-62`, called from console input and resize forwarding.

The channel's pooled async builders do not make the full input path allocation-free: whenever a send/resize is still
pending, Bridge.Wait calls ValueTask.AsTask. For an IValueTaskSource-backed operation this creates a new wrapper Task
on each call. Network/SSL backpressure can take this path during ordinary input or paste. Existing allocation tests
deliberately use a stream that completes synchronously, so they cannot detect it.

A reusable pending value-task source, completed by a blocked worker only after a continuation is registered, measures
**2,560 B for 32 waits (80 B per pending send)** in an undisturbed, warmed AllocationWindow. The fixture reuses its
source and events; it does not create a TaskCompletionSource or Task per iteration. Both focused and full-suite runs
show the same result. This is a confirmed violation of the requested hot-path allocation rule, not a claim of measured
live throughput degradation or that every real keystroke takes the asynchronous branch.

Failing test: `PveTermReviewTests.WaitingForPendingInputSendsDoesNotAllocatePerSend`.

## Console lifecycle, energy and minor qualifications

- Existing hidden-pseudoconsole tests pass for ordinary input, Ctrl+C, UTF-8/VT keys, resizing, clean EOF, API refusal,
  and restoring modes/code pages. The normal and caught-error paths dispose the front end. The input worker is a
  background thread and CONIN$ is intentionally left open until process exit; this is a process-scoped design rather
  than a reusable cancellable front-end lifetime. No additional reproducible P1/P2 close race was confirmed.
- The claim that **title** restoration happens on every control exit is broader than the code: Restore restores modes
  and code pages, while only Dispose restores the title. Open changes the title before Begin installs the control
  handler; an empty original title is also represented as null and not restored. These are minor title-restoration
  qualifications, more visible with --here, rather than additional failing P2 tests. Error strings still suggest PuTTY
  or a telnet mode that the human dropped; clean up that stale guidance.
- The pipe's first-instance flag, one-instance limit, local-client rejection, protected user-only DACL and no-read/no-write-up
  integrity label match 0036; existing tests read back the DACL/label. The client uses identification-level impersonation
  and compares the server token's user SID. Nonces are compared in constant time; a wrong nonce closes the hand-off.
  These checks were not tested with another Windows account or a deliberately lower-integrity process. ServeAsync's
  single-use bool is not an atomic concurrent-call guard, but the v1 launcher calls it once; no current-use race was found.
- No production path reviewed writes descriptors/API secrets to a file or command line. The dev helper necessarily reads
  its existing credential file; no real copy was inspected. Error paths normally print controlled messages rather than
  descriptor contents. TermproxySession's generated record ToString includes its ticket, although production currently
  does not log that object; redact it before adding diagnostic logging around the public seam.
- The current termproxy poll loop and pveproxy upgraded sockets have no post-open idle deadline. Thus 240 seconds is
  not required by those implementations. As an explicit configurable middlebox policy it is a reasonable conservative
  allowance, with 0 available for strict idle silence; actual middlebox need is not established by this review, and 0036
  correctly leaves the default's approval to the human. The implementation suppresses pings after recent sends and disables
  ClientWebSocket's default periodic pong. A queued ping does not recheck last-send time after acquiring the send lock,
  so it can occasionally follow a concurrent send unnecessarily; this is a minor extra ping, not an idle polling loop.
  Connect, hand-off and close deadlines are transient timers. No other ongoing polling loop was found.
- The separation between ITermChannel and IFrontEnd preserves the future VT seam and the user's terminal choice.
  Serial-console resize cannot change guest stty dimensions through the serial line; this is documented, not a new bug.
  The conhost viewport-only resize path and control-event restoration were inspected, not exercised with a visible window.

### N6 - P2: Handle custom escape characters that collide with command characters

Locations: `src/PveTerm/Program.cs:95-100`, `src/PveTerm/EscapeFilter.cs:44-49`.

The CLI accepts both `--escape .` and `--escape ?`, but Feed checks the quit/help commands before recognizing a
doubled escape. Consequently `..` at line start quits with `--escape .`, and `??` shows help with `--escape ?`,
instead of sending the configured character once. In the first case, quoting a literal period unexpectedly closes
the connection. The generated help also advertises the conflicting combinations as both commands and literal input.
This violates 0036's doubled-character rule for accepted custom characters.

Two deterministic filter cases reproduce this: the second Feed returns Quit or Help instead of None and one output
character. Resolve the collision consistently in parsing, filtering and help: either disallow conflicting values or
define the quoting precedence and corresponding command behavior explicitly.

Failing test (two cases): `PveTermReviewTests.DoublingACustomEscapeSendsItInsteadOfExecutingACommand`.

### N7 - P2: Do not start a blocking connect after the one-shot deadline has fired

Locations: `tools/pve-vv.py:202-213,237-239`.

The timer starts before the serving thread. If that thread (or the caller before `server.start`) is delayed until
after expiry, `expire` sets `late`, but its cancellation/disconnect have no pending connect or connected client to
terminate. `serve` then unconditionally enters synchronous `ConnectNamedPipe`. No timer remains to release that
call, and `late` is consulted only after it returns. While the launched command stays alive, the helper and pipe
can therefore outlive the advertised deadline indefinitely; a new client can still connect after expiry. This
requires an unlucky scheduling/pause ordering, not an ordinary already-connected stall, and does not defeat the
pipe ACL or nonce authentication.

The new regression deterministically forces this legal ordering: a real one-shot timer, shortened to 50 ms for
the test, completes its callback before the serving thread is allowed to start. The unmodified extracted helper
then remains pending for a 300-ms observation window, and a real local client can connect after confirmed expiry.
Connecting and closing that client releases the worker during cleanup. No artificial CPU load, terminal command,
credential-file startup or production edit is involved.

Make expiry terminal for the serving lifetime and coordinate it with I/O initiation, so cancellation cannot fall
between a state check and submission of a new blocking request. A lone pre-connect `late` check would still leave
that check/start race; holding the current gate across a blocking call would prevent the callback from cancelling
it. Use a cancellation-aware initiation/lifetime protocol.

Failing test: `PveTermReviewTests.HelperDeadlineCannotBeMissedBeforeConnectStarts`
in `tests/Pve.Term.Tests/PveTermReviewDeadlineTests.cs`.
